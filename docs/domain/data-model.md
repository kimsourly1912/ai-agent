# Data Model

Defines the tables, their relations, their constraints, and what happens when a row is deleted.
Read this before you add a table, a column, a relation, or a write. Replace every `<placeholder>` with your project's value.

## The problem this solves

A database is the last place where wrong data can be stopped. If the relation rules are unclear, code can create orphan rows, duplicate records, or history that disappears. Agents often add a foreign key without thinking about what happens on delete. This doc makes those decisions explicit.

## Mental model

- An **entity** is one kind of record, such as `<Entity>`. Each entity has one owner module.
- A **relation** links two entities. Every relation has a delete rule.
- A **constraint** is a rule the database enforces, such as "unique per tenant" or "amount is not negative."
- **History** is data that must stay explainable later. History is never deleted. A correction is a new record, not an edit of the old one.

## Flow for a change

```text
Decide the entity and its owner module
        ↓
Add the tenant column, version column, and timestamps
        ↓
Add relations with an explicit delete rule
        ↓
Add unique and check constraints
        ↓
Add indexes for the queries the feature needs
        ↓
Write a migration, and a test that proves each constraint
```

## Conventions

These apply to every table unless a row below says otherwise.

| Topic | Rule |
|---|---|
| Ids | Opaque, generated by the app (for example UUID v7). Clients never parse them. |
| Tenant | Every tenant-owned table has `tenant_id`, not null. |
| Version | Every editable table has `version`, incremented on each change. |
| Timestamps | Stored as UTC. Sent to clients as ISO 8601 strings. |
| Money | Integer minor units (for example `amount_minor`) plus a currency code. Never floats. |
| Names | Tables and columns in `snake_case` in SQL. The code may use `camelCase`, but map it in one place. |
| Booleans | Name them as facts (`is_default`). Never allow them to be null. |
| Status | Use a fixed set of values with a `CHECK` constraint. |
| Deletion | Business records are archived (`status = 'archived'`). Only records with no history may be deleted. |
| History | Never delete orders, payments, ledgers, or audit events. Correct them with a new record. |

## Relations

One row per foreign key. The delete rule is required. Do not leave it to the default.

| Child | Parent | Delete rule | Why |
|---|---|---|---|
| `<child>.<parent_id>` | `<parent>` | `restrict` | `<reason: for example, history must stay explainable>` |

Delete rules:

- **restrict**: the parent cannot be deleted while children exist. Use this for history and anything that must stay explainable.
- **cascade**: deleting the parent deletes the children. Use this only for data that has no meaning without its parent, such as a line that belongs to one list.
- **set null**: the child stays, and the link is cleared. Use this when the child must survive the parent.

## Tenant rules

1. Every tenant-owned table has `tenant_id`.
2. Every relation between tenant-owned tables stays inside one tenant. Use a composite foreign key `(tenant_id, parent_id)` where the database supports it, so a child cannot point to a parent in another tenant.
3. Every unique constraint on a tenant-owned table includes `tenant_id`. Otherwise two tenants cannot use the same name.
4. Every query names the tenant. A query without a tenant filter is a bug.

## Example (delete a parent with history)

Suppose an `order_line` refers to a `menu_item`. An order is history, so the menu item cannot be deleted while any order refers to it.

- Relation: `order_line.menu_item_id` → `menu_item`, delete rule `restrict`.
- Archive instead: setting `menu_item.status = 'archived'` hides it from new orders, and old orders still show the name they had.
- Delete: allowed only when no order line refers to the item.

## Edge cases

- **Soft delete vs. archive.** Use archive for business records a user may restore. Use permanent delete only where no history refers to the row, or where the law requires erasure. Say which one applies in the entity section.
- **Check at the database, not only in code.** A rule like "quantity is at least 1" belongs in a `CHECK` constraint. Application validation gives a better error message, but it does not replace the constraint.
- **Concurrent writes.** When two requests change the same row, the version check decides which one wins. The second request gets `409`. See `docs/standards/api.md`.
- **Adding a not-null column to a table with rows.** Give it a default, or fill it in a separate migration step before you make it required.
- **Deleting a tenant.** Decide this explicitly. Usually a tenant is suspended, not deleted, because its history must stay.
